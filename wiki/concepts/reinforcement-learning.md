# Reinforcement Learning

Learning to act by interacting with an environment and receiving reward. Formally: find a policy $\pi(a \mid s)$ maximising expected cumulative discounted reward in a [[markov-game|Markov decision process]].

> ⚠️ **This page is 63% `imported:`.** The vault holds **one** RL source — [[training-lm-follow-instructions-with-human-feedback|InstructGPT]] — and it is an application paper, not a foundational one. Everything below that is not marked as coming from that source is background knowledge, not established by anything held here. **Acquiring a foundational RL text is the highest-value next step for this cluster.** See the overview's source-acquisition section.

## The Core Objects

^[imported: standard RL formulation; no held source states it]

| Object | Definition | Question it answers |
|---|---|---|
| State value $V(s)$ | Expected return from $s$ under $\pi$ | "How good is this situation?" |
| Action value $Q(s,a)$ | Expected return from taking $a$ in $s$ | "How good is this move?" |
| **Advantage** $A(s,a) = Q(s,a) - V(s)$ | How much better than average | "Was that a good decision?" |
| Discount factor $\gamma$ | Geometric weight on future reward | Convergence, and impatience |

The Bellman equation relates them recursively — a state's value is the immediate reward plus the discounted value of what follows — and every method below is a different way of solving or approximating it.

## Three Solution Families

^[imported: the taxonomy is standard; the vault holds a source only for the third]

| Family | Learns | Needs | Held here |
|---|---|---|---|
| **[[value-iteration\|Dynamic programming]]** | $V$ or $Q$ | A known transition model | No |
| **[[temporal-difference-learning\|Temporal difference]]** | $Q$, by bootstrapping | Samples only | No |
| **[[proximal-policy-optimization\|Policy gradient]]** | $\pi$ **directly** | Samples, and on-policy data | **Yes** — via InstructGPT |

The distinction between the second and third is consequential and easy to miss.

> ### `policy-gradient-forecloses-action-valuation`
> **Policy-gradient methods optimise the policy without ever materialising per-action values, so a framework built on them cannot be repurposed to score individual actions. The algorithm family silently determines what analysis is available downstream.**
> ^[generated: drawn from the contrast between the families. rests-on: imported:rl-family-taxonomy]

A value-based method hands you $Q(s,a)$ for every action — which is what makes counterfactual action scoring possible. A policy-gradient method hands you $\pi(a \mid s)$ and nothing else.

## On-Policy and Off-Policy

^[imported]

Whether a method learns from data generated by the policy it is improving.

| | On-policy | Off-policy |
|---|---|---|
| Learns from | Its own current behaviour | Any behaviour, including logged data |
| Sample efficiency | Poor — data is discarded after each update | Better — [[proximal-policy-optimization\|replay]] is possible |
| Examples | SARSA, [[proximal-policy-optimization\|PPO]] | Q-learning, [[deep-q-network\|DQN]] |
| Converges toward | Value of the **behaviour** policy | Value of the **optimal** policy |

The last row is the interpretive one. **An on-policy method describes what an agent does; an off-policy method prescribes what it should do.** Where the goal is measurement rather than control, the distinction determines what the output means. See [[policy-modelling]].

## The One Held Application

[[training-lm-follow-instructions-with-human-feedback|InstructGPT]] is the vault's only RL source, and it is unusual in three ways worth stating:

1. **The reward is learned**, not specified — a reward model trained on human preference comparisons. That is closer to inverse RL than to standard RL.
2. **The environment is a single step.** A language model emits a completion and receives a score; there is no state transition to reason about.
3. **The policy is anchored** to its starting point by a [[kl-divergence|KL]] penalty, so the objective is not pure reward maximisation.

So the vault's grounding in RL is an atypical instance. Read [[proximal-policy-optimization]] and [[rlhf]] with that in mind.

## Why Reward Is Hard

^[imported: the reward-specification problem is well established but not by any held source]

Two failure modes recur wherever RL is applied:

**Sparse reward.** If reward arrives only at the end of a long episode, credit assignment across the intervening actions is underdetermined. Standard responses are discounting, reward shaping, and substituting a frequent correlate for a rare target — see [[rare-event-proxy-targets]].

**Reward hacking.** A policy may find behaviour scoring highly on the specified reward without satisfying the intent behind it. InstructGPT is explicit that its learned reward model is gameable; this is the same problem that makes [[imitation-learning|imitation]] an attractive alternative when demonstrations exist.

## Where RL Sits Against Its Neighbours

| | Learns from | Optimises |
|---|---|---|
| **Reinforcement learning** | Reward signal | Expected return |
| [[imitation-learning]] | Demonstrations | Match to observed behaviour |
| Inverse RL | Demonstrations | A **reward** explaining them |
| Supervised learning | Labels | Match to labels |

[[rlhf|RLHF]] straddles the middle two — a reward is learned from human preference (inverse-RL-flavoured), then optimised against (RL).

## Limitations

- **Sample inefficiency.** RL typically needs orders of magnitude more interaction than supervised learning needs labels.
- **Simulator dependence.** Interaction must be cheap, which usually means simulated — and a policy optimised in a simulator is optimal for the simulator. See [[agent-based-simulation]] and [[domain-adaptation]].
- **Instability under function approximation.** Bootstrapping, off-policy data and neural approximation together are known to diverge; the [[deep-q-network|DQN]] stabiliser set exists to manage this.
